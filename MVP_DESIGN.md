# Christmas mosaic MVP design

## Resolution extension: 3×3 colours per original position

The latest village trial retains the 5×5 daily layout and subdivides every original position into 3×3 independent colour cells. Geometry is now selectable using `--subdivision 1` (original mode) or `--subdivision 3`:

| Property | Original | Subdivision 3 |
| --- | --- | --- |
| Full mosaic | 45×45 | 135×135 |
| Daily tile | 9×9 | 27×27 |
| Colour cells per day | 81 | 729 |
| Total colour cells | 2,025 | 18,225 |
| Original positions per day | 9×9 | 9×9, each enclosing 3×3 colours |

Process the saved original source at the chosen resolution; never upscale the coarse mosaic as the source of extra detail. Each fine cell still maps to exactly one palette entry. The same tile/day ordering applies, with tile boundaries every 27 pixels at subdivision 3. Original local position `(x,y)` contains fine coordinates `(3x+dx,3y+dy)` for `dx,dy` in `0..2`.

New `mosaic.json` files use schema version 2 and store `subdivision` alongside actual geometry. The validator continues to accept older runs without this field as subdivision 1. Run settings also record subdivision and must agree. Minimum source dimensions equal the target dimensions. Previews use exact nearest-neighbour enlargement: 20× for the original mode, 8× for the fine mode.

Guides include both coloured reference pages and numbered white colouring pages, one 27×27 grid per day, with heavy lines every three cells. Two-digit print numbers map to palette IDs through a legend repeated on each day page. The fine A4 grids use 6 mm cells (162 mm grid width before borders), allowing 6.5 pt numbers. At this print size each original position is 18 mm wide. Inventories count fine cells, including white. HTML is generated by the pipeline; PDFs for this trial were exported with Chrome and checked for one cover plus 25 day pages.

The original baseline specification below remains as historical context; the geometry and guide extension above takes precedence for subdivision 3.

## Scope and decisions

Build a small local pipeline that accepts an AI-generated Christmas illustration and produces an exact, buildable mosaic. The first milestone is a feasibility experiment, not a web application. The local pipeline and marker extraction are now implemented; see the README for commands and finished examples. The first user-requested trial contains two independently generated scenes, one per marker palette, rather than the three-candidate experiment proposed below. Human recognition and assembly evaluation remain pending.

Use Python and Pillow for image loading, normalization, resizing, and PNG export, with standard-library JSON/CSV support. Image generation is a separate step: initially use an available image-generation tool or interface and save the source locally. An automated provider adapter can follow once the experiment works; API credentials are not required by the image-processing stage.

Fixed geometry:

- Mosaic width and height: 45 cells each.
- Tile arrangement: 5 columns × 5 rows.
- Tile width and height: 9 cells each.
- Total: 25 tiles × 81 cells = 2,025 filled positions.
- Each cell stores one colour ID from a fixed 13-entry palette. No transparency, blended cells, or empty positions.

Use 25 advent days, December 1–25, in row-major order for the trial. Numbers and tile borders belong on separate instruction sheets, never in the 45×45 artwork. Alternative reveal orders and 24-day packaging are outside this trial.

## Fixed palette

The original design used the following **provisional digital palette**. Product photographs have since supplied two alternatives: [FriXion](palettes/frixion.json) and [ClickArt](palettes/clickart.json). Prefer one of these for marker-based trials, combining its separate white entry with its 12 ordered marker colours. These are photographed plastic colours, pending confirmation against ink on paper. Keep IDs stable within the selected palette across image data, guides, and inventories; an ID does not denote the same colour in different palettes.

| ID | Name | sRGB hex |
| --- | --- | --- |
| C00 | White | `#FFFFFF` |
| C01 | Black | `#171717` |
| C02 | Dark blue | `#183153` |
| C03 | Blue | `#2864B4` |
| C04 | Light blue | `#8BC6E8` |
| C05 | Dark green | `#174D2A` |
| C06 | Green | `#398A42` |
| C07 | Red | `#C92A32` |
| C08 | Dark red | `#7E2030` |
| C09 | Yellow | `#F4CD45` |
| C10 | Orange | `#E88932` |
| C11 | Brown | `#805333` |
| C12 | Light grey | `#C6CBCF` |

Each run’s `palette.json` contains a version, colour space (`sRGB`), and an ordered array of these IDs, names, and hex values. Validate exactly 13 unique IDs and 13 unique RGB values, including exactly one pure white entry. All other entries must be non-white. Do not learn a new palette from each image or require every allowed colour to appear.

The first test assumes sufficient pieces of every colour. Inventory output reveals demand; stock-constrained recolouring is a later feature. Digital previews cannot establish physical colour fidelity without a sample build.

## Scene coherence requirement (revised after sampler trial)

The completed 45×45 image must read as one continuous Christmas scene. A quilt of independent daily icons does not meet the objective. Compose substantial objects throughout the canvas on a shared ground plane, with buildings, decorations and paths naturally crossing daily tile boundaries. Minimize empty sky and snowfields. Individual days should reveal meaningful parts of the scene where possible and otherwise offer substantial colour variety. Do not enforce self-contained objects or separate backgrounds within each 9×9 area.

The village trial combines connected rooftops, market stalls, decorated trees, presents and snowy paths. Its exported daily colour reports screen for empty days, while scene coherence and recognition remain human judgements. Earlier landscape and sampler results are preserved for comparison.

## Daily interest requirement (revised after landscape trial)

Each advent day should ideally make sense as its own 9×9 picture. Otherwise it should at least offer meaningful colour variety. A recognisable overall landscape does not satisfy this requirement if many days are empty sky, snow, or disconnected fragments.

The second trial uses a 5×5 Christmas sampler with one simple motif per tile and no gutters. Source prompts request at least four substantial colours per motif and contrasting backgrounds. Review the exact exported tiles: generation does not guarantee these constraints. The tile-review script reports distinct colours, colours used by at least three cells, and dominant-colour share; these are diagnostics, not acceptance gates or substitutes for human review.

For pixel-style sources, the converter now offers `--resampling nearest` as an explicit alternative to the default BOX reduction. It preserves sampled source colours before palette mapping, avoiding blended boundaries at the cost of potentially losing narrow features. The chosen method is recorded and used in deterministic revalidation. Both variants of the sampler trial are preserved.

## Source generation

Generate three independent candidates using the same scene brief. Request a square image at a supported resolution, preferably at least 512×512. Keep the original output unchanged. Do not rely on the generator to return an exact pixel grid or exact RGB values.

Use this prompt, appending the palette names and hex values from the selected palette configuration:

> Create a square, flat-colour Christmas illustration that will be reduced to a 45 by 45 pixel mosaic. Show one large decorated evergreen Christmas tree on the left, a small red cabin with a bright yellow window on the right, a broad white snowy foreground, and a dark blue winter sky. Put a simple yellow star on the tree. Use a small number of large, solid shapes, crisp silhouettes, and strong contrast between neighbouring objects. Keep the tree and cabin comfortably inside the frame. Make the tree the dominant subject and the cabin clearly secondary. Essential features should remain visible when the whole picture is only 45 pixels wide; make important details several pixels wide at that final scale. Use the supplied palette as a colour guide. Avoid gradients, photorealism, texture, tiny ornaments, scattered snow speckles, text, numbers, borders, grid lines, perspective tile boards, and mockups. Return only the flat artwork, filling the square image.

Save the exact submitted prompt, provider/tool and model identifier if available, requested options, generation timestamp, and returned source filename. Record a seed only if the provider exposes one; generation need not be reproducible. Preserve the source bytes and their SHA-256 hash so downstream conversion can be reproduced without another generation call. Never store credentials in the run metadata.

The three candidates are a bounded initial experiment. Inspect the processed mosaics, not just the attractive source images. If none pass, simplify the scene brief and record that as a new experiment instead of silently editing the output.

## Deterministic conversion

### 1. Validate and normalize

Load the image, reject unreadable or multi-frame inputs, and apply EXIF orientation. Convert images with an embedded supported colour profile to sRGB; treat untagged RGB images as sRGB and record that assumption. Reject unsupported colour conversions with an actionable error. Composite transparency onto pure white and work in opaque RGB.

Require a square image of at least 45×45 pixels after orientation. Reject a non-square image by default. An explicit centre-crop option may take the largest centred square, recording the crop rectangle; never stretch the scene or silently crop it. If cropping loses a subject, regenerate the source.

### 2. Reduce to the cell grid

Resize the normalized square to exactly 45×45 using Pillow's `Image.Resampling.BOX`. This is the baseline downsampling choice; averaging source regions helps broad shapes survive. The reduced RGB image is intermediate data and may contain colours outside the palette.

Pillow documents resizing and the available resampling filters in its [Image reference](https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.resize). Use `NEAREST` only when enlarging finished cell art for previews so each cell stays a solid square.

### 3. Quantize to the supplied palette

For each reduced RGB pixel `p`, choose the palette entry `c` minimizing:

```text
distance(p, c) = (p.r - c.r)^2 + (p.g - c.g)^2 + (p.b - c.b)^2
```

Use integer channel values in encoded sRGB and break ties by palette array order. Store the winning colour ID in a 45-row × 45-column matrix. This direct nearest-colour implementation is small and unambiguous at 2,025 × 13 comparisons; an adaptive “reduce to 13 colours” call does not satisfy the fixed-palette requirement.

No dithering or error diffusion is applied. Do not interpolate, smooth, or antialias after quantization. Encoded RGB distance is a simple baseline, not a perceptually uniform measure; if colour assignments hurt readability, compare a documented perceptual distance in a later experiment while keeping the same palette and source.

### 4. Render and split

Render `mosaic.png` by looking up the exact RGB triple for every stored colour ID. Save as an opaque RGB PNG with dimensions 45×45. The ID matrix is authoritative; all other outputs derive from it.

Coordinates are zero-based with origin at the top left, `x` increasing rightward and `y` downward. Store cells as `cells[y][x]`. For tile column `tc` and tile row `tr` in `0..4`:

```text
day = tr * 5 + tc + 1
tile[local_y][local_x] = cells[tr * 9 + local_y][tc * 9 + local_x]
```

Local coordinates run from 0 to 8. Day 1 covers global x/y 0–8; day 5 covers x 36–44 and y 0–8; day 25 covers x/y 36–44. Each tile export is an exact 9×9 PNG. Reassembling the 25 exports without gaps must reproduce the finished image pixel for pixel.

## Outputs and interface

Implemented local command interface:

```sh
python -m mosaic build --source inputs/christmas-01.png --palette palette.json --output runs/christmas-01
```

Repeat for each candidate. Refuse to overwrite an existing run directory by default. Invalid inputs fail with a nonzero exit status and an explanation; only mark a run successful after output validation passes.

Each successful run contains:

| Artifact | Contents |
| --- | --- |
| `source.png` or original source extension | Unmodified source bytes |
| `normalized.png` | Square, opaque sRGB source used for resizing |
| `reduced.png` | 45×45 RGB image before quantization, for diagnosis |
| `palette.json` | Exact ordered palette snapshot |
| `mosaic.json` | Schema version, geometry, palette, and 45×45 colour-ID matrix |
| `mosaic.png` | Canonical exact 45×45 RGB artwork, without guides |
| `preview.png` | 900×900 nearest-neighbour enlargement; 20 pixels per cell |
| `assembly.html` | Self-contained printable overview, palette legend, and 25 tile guides |
| `tiles/day-01.png` … `tiles/day-25.png` | Exact 9×9 tile images |
| `inventory.csv` | Overall and per-tile counts for every palette ID, including zero counts |
| `run.json` | Prompt, available generation metadata, source hash, conversion settings, dependency versions, and validation results |

Each tile guide displays its day number, tile row/column, fixed “top” orientation, a 9×9 grid with colour IDs in the cells, and per-colour piece counts. Use legible contrasting label text. Label text and grid strokes may use display colours outside the palette because they are instructions, not mosaic cells. Include an assembly map showing where all 25 days belong.

Include geometry fields `width=45`, `height=45`, `tile_width=9`, `tile_height=9`, `tile_columns=5`, and `tile_rows=5` in `mosaic.json`. In `inventory.csv`, use columns `scope,day,colour_id,count`, with `scope` either `overall` or `tile`; leave `day` empty for overall rows. Counts include white, since every position must be filled.

## Validation and feasibility test

Automated validation must reload the saved artifacts and establish:

1. The canonical PNG is exactly 45×45 and opaque RGB, with every pixel an exact member of the saved palette.
2. The JSON matrix has exactly 45 rows of 45 valid colour IDs and reconstructs the PNG exactly.
3. There are exactly 25 tile PNGs, each 9×9, with unique day numbers 1–25; reassembly matches the canonical PNG.
4. Every tile inventory totals 81; overall inventory totals 2,025; each colour's tile totals equal its overall count and the PNG count.
5. The preview consists solely of exact 20×20 copies of canonical pixels.
6. Repeating conversion with identical source bytes, palette, settings, and dependency versions produces identical cell IDs and pixel values. Metadata timestamps and encoded file bytes need not match.

Implementation tests should cover palette rejection, invalid input geometry, transparent input compositing, exact palette matches, distance ties, and tile boundary/orientation errors. Use an asymmetric synthetic cell pattern to catch transposed or reversed tile assembly. These tests validate correctness; they do not prove that the artwork is good.

For the first feasibility session:

1. Generate the three candidates and convert each with the same palette and baseline settings. Record generation effort, processing time, and cost if available.
2. Show unlabelled mosaic previews to three people before showing the sources or scene brief. Record what they recognise.
3. A candidate passes visual recognition if at least two reviewers independently identify a Christmas/winter scene, a decorated tree, and a cabin or house. Review at both native size and an enlarged cell view; score recognition using the enlarged view that represents the assembled mosaic.
4. Ask reviewers whether single-cell noise, merged silhouettes, or lost details interfere with recognition. Record issues alongside the corresponding source and reduced image.
5. Have one person follow the guide for a tile containing several colours, then place it on the assembly map. A guide passes if they complete all 81 positions and orient the tile correctly without verbal clarification. Use physical materials when available, otherwise a paper or digital simulation and label the result accordingly.

The MVP passes digital feasibility if at least one candidate passes all automated checks, visual recognition, and the guide trial. A physical sample remains necessary to confirm material colour match and handling if the trial was simulated. If no candidate passes, retain the failed runs and report the failure mode before changing the prompt, palette, or mapping method.

## Implementation sequence and exclusions

1. Implement palette loading, normalization, resizing, and explicit nearest-colour assignment against a saved source.
2. Add canonical exports, tile splitting, guides, inventories, and artifact validation.
3. Generate and preserve three Christmas sources, run the conversions, and perform the feasibility session.

Defer a web UI, automated generation API integration, interactive pixel editing, stock optimization, alternative grid sizes, packing/shipping design, and sophisticated reveal orders. The central risk is loss of readable shapes at 45×45; the small candidate experiment is intended to expose that before expanding the product.
